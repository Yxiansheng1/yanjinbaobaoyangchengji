# 情侣看看 · v0.1 方案（作废）

> 目标：两台手机装上，打开就能看到对方。
> 周期：2~3 周（按每天 2~3 小时算）
> 本阶段**不写的功能**，见文末「明确不做」。

---

## 1. 范围：12 个功能点

| 编号 | 功能 | 为什么放在第一版 |
| --- | --- | --- |
| H1 | 注册登录（邮箱 + 密码） | 没有账号，换手机数据就没了 |
| H2 | 配对绑定（配对码） | 两个人的关系的载体 |
| H4 | 服务器 | 一切的底座 |
| H5 | 安卓后台常驻 | 不加这个，锁屏就断，其他都白搭 |
| A1 | 实时位置 | 核心 |
| A2 | 地点语义（在公司/在家） | 只有坐标没有意义 |
| A9 | 电量 / 充电 | 便宜、有用、所有人都做 |
| A10 | 正常共享（幽灵模式默认档） | 作为 G1 的对照组 |
| G1 | 一键暂停共享 | 没有它，产品会让人想卸载 |
| B1 | 今日屏幕时间 | 核心 |
| B2 | 应用使用排行（Top 5~15） | 核心 |
| B5 | 首次 / 末次解锁时间 | 一句话就能看懂今天的作息 |

**为什么是这 12 个**：去掉任何一个，App 都不成立；再加任何一个，都会拖长第一版的周期。

## 2. 三端边界

| 端 | 是什么 | 干什么 |
| --- | --- | --- |
| 她的安卓 | 原生 App（Kotlin） | 采集全部数据 + 也能看对方 |
| 他的 iPhone | 原生 App（SwiftUI） | 上报位置/电量/步数 + 看对方 |
| 服务器 | 自建后端 | 存储、转发、鉴权 |

iPhone 端在 v0.1 只上报：位置、电量、步数。屏幕时间等 B 类数据 iOS 拿不到，不做。

## 3. 技术选型

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 安卓 | Kotlin + Jetpack Compose | 功能多，Compose 长期更好维护 |
| 安卓定位 | 高德定位 SDK | 比系统 API 省电、准、自带逆地理编码 |
| 安卓地图 | 高德地图 SDK | 国内可用，个人开发者免费额度够 |
| 安卓存储 | Room | 离线补传队列 |
| 安卓网络 | Retrofit + OkHttp + WebSocket | |
| iOS | SwiftUI + CLLocationManager + CoreMotion | |
| 后端 | Node.js + Fastify + SQLite + WebSocket | 两人用，SQLite 足够；备份=拷一个文件 |
| 部署 | 一台 VPS + Docker | |
| 推送 | v0.1 不做（v0.2 和 C 类一起） | |

## 4. 数据模型

```
users        id, email, password_hash, nickname, avatar, created_at
couples      id, user_a, user_b, status, created_at
devices      id, user_id, platform, push_token, app_version, last_seen_at
pair_codes   code, user_id, expires_at, used

-- 高频写入，只保留 7 天
location_points  id, user_id, lat, lng, accuracy, speed, provider,
                 battery, charging, recorded_at
                 index (user_id, recorded_at)

-- 日报，一天一行
daily_usage  id, user_id, date, screen_on_ms, unlock_count, lock_count,
             first_unlock_at, last_unlock_at

-- 每应用每天一行（只存 Top N，避免爆量）
app_usage    id, user_id, date, package_name, app_label,
             foreground_ms, launch_count

-- 当前状态，反范式，读一次就够
user_status  user_id, lat, lng, place_name, battery, charging,
             online, paused_until, updated_at

settings     user_id, share_location, share_usage, share_battery
```

**关键设计**：`user_status` 是反范式表。地图首页只查它一张表，不做聚合。否则每次刷新都要扫几十万行位置点。

**位置点保留 7 天**，定时任务清理。这是 A5 历史轨迹的基础，也是隐私上的合理默认。

## 5. 接口

```
POST   /auth/register          { email, password, nickname }
POST   /auth/login             { email, password } -> token

POST   /pair/code              -> 6 位配对码（10 分钟有效）
POST   /pair/accept            { code }

GET    /partner/status         -> 位置、电量、在线、是否暂停、地点名
GET    /partner/usage?date=    -> 屏幕时间、解锁、Top 应用
PATCH  /settings/share         { share_location, share_usage, share_battery }
POST   /settings/pause         { until }

POST   /sync/location          批量上报（最多 50 条/次）
POST   /sync/usage             日汇总 + Top 应用

WS     /ws                     实时推送位置变化
```

**同步策略**：本地先写 SQLite，联网后批量补传。断网 30 分钟不丢数据。

## 6. 验收标准（v0.1 算做完的定义）

1. 两台手机各自注册、输入配对码，绑定成功
2. 她锁屏 30 分钟后，位置仍在更新（说明后台没被杀）
3. 他打开 App，1 分钟内看到她的最新位置、地点名、电量
4. 他看到她的今日屏幕时间、Top 5 应用、首次/末次解锁时间
5. 她点「暂停共享」→ 他那边立刻显示「已暂停」，位置不再更新
6. 断网 30 分钟再恢复，期间的轨迹能补传上来
7. 她的手机连续跑 24 小时，耗电增加不超过 8%

第 2、6、7 条是真正的门槛，也是最容易翻车的地方。

## 7. 需要拍板的三件事

### ① 服务器放哪

| 方案 | 成本 | 备案 | 延迟 |
| --- | --- | --- | --- |
| 国内 VPS + IP 直连 | ~30 元/月 | 不用 | 最好 |
| 国内 VPS + 域名 | ~30 元/月 + 域名 | **要，2~3 周** | 最好 |
| 香港/新加坡 VPS + 域名 | ~35 元/月 | 不用 | 50~100ms，够用 |
| Supabase / Cloudflare 免费档 | 0 | 不用 | 国内不稳，实时会卡 |

**建议：香港 VPS + 域名。** 不用备案，两个人用完全够，出问题自己能登上去看。

### ② 地图 SDK 的 key

高德开放平台个人开发者注册免费，要实名认证。申请「Android 地图 SDK」和「Web 服务」两个 key。**这一步要你本人操作**，我没法代注册。

### ③ iOS 编译管线

v0.1 先只做安卓。iOS 排在 v0.2 之后，因为云编译 + AltStore 那套要单独折腾，不该卡住主线。

## 8. 明确不做（v0.1）

- 任何推送通知（C 类全部）
- 历史轨迹界面（A5 只存数据，不做 UI）
- 幽灵模式的模糊/冻结（A11/A12）
- 聊天、贴纸、互动（D 类全部）
- 纪念日、相册、时间线（E 类全部）
- 养成、打卡、积分（F 类全部）
- 应用分类统计、趋势对比（B7/B8）
- iOS 端（v0.2 之后）
