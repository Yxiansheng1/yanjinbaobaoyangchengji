## 一句话结论

十二条里九条是我写错了，两条属于范围取舍，一条是产品决定。整体质量高于一般的文档走查：它抓到的四个问题（权限绕过、配对唯一性、快照乱序、无数据状态判不出来）都不是措辞层面的，是会让产品在真机上出错的。

## 我顶回去的一条

**R06 里「把单方解除关系纳入最小版本」不采纳。**

三条理由：

第一，这件事已经有替代品，而且更符合产品性格。暂停是一键的、对方立刻看到、双方都可逆。解绑是不可逆的，第一版就摆一个不可逆按钮在设置里，出事成本远高于收益。

第二，代价被低估了。解绑要定义清楚：谁发起、要不要对方确认、确认前数据怎么算、关系结束后历史数据删还是留、留存多久、删了能不能恢复。这五个问题每个都要拍板，不是加个接口的事。

第三，v0.1 的用户只有两位，且都是自愿装这个 App 的人。给他们一个「删掉一切」的入口，实际使用频率接近零，但它带来的实现分支和验收项是实打实的。

我的替代方案：v0.1 的暂停提供「手动恢复」档，效果等价于「我不想被看了」，且对方能看到这个事实。真正解绑排 v0.4，和删号、数据处置一起设计。

如果你坚持要进 v0.1，我照做，但会先要你回答上面那五个问题。

## 我认为审查本身偏了的三处

**第一，R11 提了「60 秒」这个数，但那是我的原稿，不是它的建议。** 它指出「60 秒误差评价不了 Top 15 排名对不对」是对的，于是我拆成了两条门槛：时长误差 60 秒、排行集合与顺序一致。但新阈值实际上还是我定的，审查没有给替代值。这类「指出问题但不给答案」的条目，不能当成可以直接照抄的修改单。

**第二，R05 要求「每个指标都写明分位数」，我不全接受。** 延迟这种抖动量确实该看 P95；但耗电、补传完整率、崩溃次数这类累计量，用单值更可判，套上分位数反而弱化了门槛。所以第 12 节里只有延迟写分位数，其余仍是单值。

**第三，R06 把解绑列为「与允许用户退出共享的原则不一致」，这个推理跳了一步。** 原则说的是「能退出」，不是「能删除关系」。暂停就能退出共享。审查把两个不同层级的动作混成一件事，这处我保留意见。

## 我借这次审查又发现的三个问题

**一，改函数返回类型必须先 drop。** 这条不是审出来的，是我自己执行时撞上的：002 的 `report_locations` 返回 `int`，003 要返回 `jsonb`，`create or replace` 直接报 42P13。已经修好，但这个教训要写进流程：契约层改签名，迁移脚本里必须有 drop，不能只写 create or replace。

**二，`report_usage` 用 -1 表示「旧快照被丢弃」，是语义混用。** 一个 int 既表示行数又表示拒绝原因，客户端要写 `if (ret < 0)` 这种判断，容易看漏。更干净的做法是返回 `{accepted, rows}`。我先不改，理由是：现在改会让刚跑完的迁移再动一次函数签名，而这个混用只要文档写清就不会误用。如果你觉得这个理由不够，我改。

**三，双写不一致的风险只被缓解，没被消除。** `set_pause` 在一个事务里改状态表和存在表，这解决了暂停本身；但上报路径是「写点表 + 写状态表 + 写存在表」，三处任何一处失败，就会出现「有点但状态没更新」。已用单函数单事务覆盖主要路径，仍需要在 W-18 里做一次故障注入验证。

第三方复核只挑出 T01–T04 四件事，没有推翻权限方案。T01 我认，而且是我自己写验收写错了。

V20 原文写「只关采集，对方就看到未共享」，但 D14 与第 6 节一直说采集和共享是两件事。等于是我一边冻结「只停上报、不改共享」，一边拿验收去要求相反的行为。实现没错，验收错了。现在拆成 V20「关闭采集」与 V21「纯查看模式」，并写清一键操作的顺序、部分失败和重试。T02 是测试名称大于实际动作，四处逐个改，另把 N05 的时间依赖换成独立日期。T03 的并发与 Realtime 照旧只能在线上验。T04 是 README 和第 4 节标题的旧文字。

**配对码并发生成我不当缺陷修。** 两个请求可能各生成一个有效码，但这不造成越权：已配对的人接受新码会被 `partner_already_paired` 挡住。004 再补用户行锁或唯一活动码约束。这轮没有改 SQL，线上不用重跑。

## 第二轮：这次是我错了

二次复核比第一轮狠，而且狠得对。N01 和 N02 不是措辞问题，是会直接漏数据的实现错误。

N01 是 PL/pgSQL 的三值逻辑：未配对时 `my_partner_id()` 返回 null，`x <> null` 是 null，`TRUE AND NULL` 还是 null，`IF` 直接不进拒绝分支。我写第一版时把「条件为假」和「条件为 null」当成一回事了。

N02 更难看：我为了修 R01 收回对象对 `user_status` 的读权限，结果让历史位置策略里那句 `not exists (... from user_status ...)` 恒为真，亲手把暂停判断拆了。这说明「在调用者看不见的表上做否定判断」本身就是错的，不是漏了一个 `and`。所以这次不补条件，直接把四张原表对对象全部关掉，只留两个函数入口。

N03、N04、N05、N06、N07 我都认，没有一条需要争。N08、N09 是文档口径，也认。

第一轮里我顶回去的 R06、被收窄的 R05、被指出没给替代值的 R11、以及 R04 的关闭，复核方自己更正了，我接受，不再重复论证。

## 修的时候又发现五个自己的问题

**一，`set_pause` 会改 `user_status.updated_at`。** 这是跑 N06 用例时暴露的：暂停和恢复都写 `now()`，恢复后的旧点看起来比 `resumed_at` 还新，遮蔽条件正好失效。已改成暂停只写 `paused_until`，`updated_at` 永远只表示最后一点的采集时刻。

**二，生成配对码的 upsert 会抢别人的码。** 原写法随机撞到已存在的码时，直接 `do update set user_id = excluded.user_id`。两个用户同时抽到同一个六位数，后写的会把前一个人的码改到自己名下。改成 `on conflict do nothing` 后重试，概率极低但代价为零。

**三，纯查看模式不能只靠界面。** 只在设置页关开关，队列里的旧点还会继续上传。现在 `collect_enabled = false` 时服务端直接拒绝两个上报函数，设备端和云端各有一道。

**四，客户端能直接写表。** 复核在「对修改者新增判断的核对」末尾提了一句「直接表写入绕开函数」要单独查。查下来四张数据表都留着写自己的策略：纯查看模式只挡了函数，直写照样能落数据；`daily_usage` 直写还能绕过版本比较。现在写策略删掉，`authenticated` 与 `anon` 的写权限也收回，直写直接报 42501。

**五，成员表回填还在用 `on conflict do nothing`。** 我一边在文档里写「不掩盖」，一边代码里还在跳过冲突，说法和实现对不上。现在改成先跑三项一致性检查，把冲突的用户和关系 id 列出来再报错。

## 我保留的两点

**N05 我只敢说「结构上修了」，不敢说「并发验过了」。** 本机 PGlite 是单连接，两个独立连接的竞争我没复现。原子性来自「比较写进 UPSERT 的 WHERE」，这是 PostgreSQL 的语义，不是我的测试结果。所以线上必须按 V14 再跑一次，跑之前我不把它标成已验证。

**N08 的 60 秒我没有换数。** 复核方说「不要凭空换一个数」，我同意，所以规格里改成「先测三天偏差再决定是否保留 60 秒」，并把 V6 与第 12 节的容差写成同一口径。这不是拖延，是不想用一个没有数据支撑的新数字替代旧数字。
