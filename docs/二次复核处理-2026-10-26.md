## 逐项

### N01 未配对账号可读指定用户状态

**成立，是我的错。** 原判断 `if v_target <> v_uid and v_target <> my_partner_id() then` 在未配对时是 `TRUE AND NULL`，PL/pgSQL 的 `IF` 不进入拒绝分支，查询照跑。

改法：

```sql
v_partner := public.my_partner_id();
v_target  := coalesce(p_user_id, v_partner);
if v_target is null then return; end if;
if v_target <> v_uid then
  if v_partner is null or v_target <> v_partner then
    raise exception 'not_allowed';
  end if;
end if;
```

`get_usage` 用同一套判断。

本机结果：未配对 C 调 `get_status(A)`、`get_usage(A)` 都是 `not_allowed`；已配对 B 调 `get_status(D)` 也是 `not_allowed`；C 无参调用返回空集。

### N02 暂停仍能读历史位置和用机

**成立，而且是我修 R01 时自己拆出来的。** 收回对象对 `user_status` 的读权限后，历史位置策略里 `not exists (select ... from user_status where paused_until > now())` 恒为真，暂停判断被反向绕过。

改法不是补条件，是把入口收干净：

- 删除对象对 `user_status`、`location_points`、`daily_usage`、`app_usage` 的全部 SELECT 策略。
- 当前状态只走 `get_status`，用机只走 `get_usage`，暂停判断写在函数体里。
- `location_points` 保留「本人可读」，给 v0.3 轨迹用。

本机结果：暂停后 B 直查四张表都是 0 行；`get_usage` 返回空；`get_status` 坐标、精度、地名、电量全为 null，`paused_until` 仍可见。

### N03 关闭电量共享仍泄露历史电量

**成立。** 历史位置整行里带 `battery` 与 `charging`，原策略只判 `share_location`。

改法与 N02 同一处：对象根本读不到 `location_points`，历史电量没有单独开口。当前电量仍由 `get_status` 按 `share_battery` 遮蔽。

本机结果：A 设 `set_sharing(true,true,false)` 后，B 的 `get_status` 位置可见、电量与充电为 null；B 直查 `location_points` 为 0 行。

### N04 成员表允许用户伪造关系

**成立。** 原 INSERT 策略只检查 `user_id = auth.uid()`，不检查 `couple_id` 是否真包含自己；`my_partner_id()` 又只看成员表，不看 `couples` 两侧。

改法：

- 删除 `couple_members` 的 INSERT 策略，普通用户没有任何写入通道，只有 `accept_pair_code` 这个 SECURITY DEFINER 函数能写。
- `my_partner_id()` 增加 `(c.user_a = auth.uid() or c.user_b = auth.uid())`，孤儿成员行返回 null。
- 回填前做三项检查，任何一项不满足就把要修的行列出来并 `raise exception`，不用 `ON CONFLICT DO NOTHING` 盖住：一人多段 active 关系、自己配自己、已有成员行与 active 关系不一致（含伪造行与指向失效关系的行）。

本机结果：C 插入成员行被 RLS 拒绝（`new row violates row-level security policy`）；C 的 `my_partner_id()` 为 null；A、B 两侧互为对象。

### N05 快照版本检查的并发窗口

**成立。** 原写法是先 SELECT 比版本，再无条件 UPSERT，两个请求可以同时判定自己可写。

改法：把比较放进冲突更新条件，读与写在同一条语句内完成。

```sql
on conflict (user_id, date) do update
  set ...
  where du.captured_at is null or excluded.captured_at >= du.captured_at;
get diagnostics v_ok = row_count;
if v_ok = 0 then return -1; end if;
```

用 `>=` 而不是 `>`，是为了让同一版本的网络重发按幂等成功处理，而不是被当成旧快照拒绝。旧快照仍然严格小于，返回 -1。

本机结果：先发 10:15 返回 1，再发 10:00 返回 -1，库里仍是 10:15；同版本重发返回 1，应用明细仍是最新一版。**并发两连接未实测**，这是静态结论，线上要按 V14 补一次。

### N06 恢复后立即返回旧坐标

**成立。** 恢复只清 `paused_until`，旧点还在 `user_status` 里，下一次 `get_status` 就把它当当前点返回。

改法：

- `presence` 增加 `resumed_at`，手动恢复时写入。
- `get_status` 在三处遮蔽坐标：`paused_until > now()`；`paused_until` 已过但最后一点采集于它之前；`resumed_at` 晚于最后一点。
- 定时到期不写 `resumed_at`，靠 `paused_until` 与 `user_status.updated_at` 比较。

修这一条时又发现一个自己的错误：`set_pause` 原来会顺手把 `user_status.updated_at = now()`。这会让恢复后的旧点看起来比 `resumed_at` 还新，遮蔽条件正好失效。已改成只写 `paused_until`，`updated_at` 永远只表示最后一点的采集时刻。这个问题是跑本机用例时暴露的，不是文档推出来的。

本机结果：暂停后恢复，B 拿到 lat/lng 为 null；A 上报新点后立刻可见；定时暂停到期后同样先返回 null，新点到达才显示。

### N07 发布范围和新用户初始化

**成立。** 原脚本只 add `presence`，没有 drop `user_status`、`location_points`；`handle_new_user` 也没建 presence 行。

改法：

- 发布集合 drop 掉 `user_status` 与 `location_points`，只留 `presence`。
- `handle_new_user` 同时建 `settings`、`user_status`、`presence` 三行。
- `set_pause`、`set_sharing`、`set_collect_enabled` 全部改 UPSERT，即使触发器漏了也不会静默无信号。

本机结果：`pg_publication_tables` 只剩 `presence`；003 之后新注册的用户有 presence 行，首次定位前切暂停也会更新 `updated_at`；未配对账号查对方 presence 为空集，对象读得到。

**线上 Realtime 消息体没有抓**，本地不跑 Realtime 服务。这一条按 V19 在线上补。

### N08 统计验收的共同口径

接受「先建立相同统计定义，再定阈值」。规格第 9 节新增一组固定输入与期望输出：

- 跨零点连续亮屏 20 分钟，按半开区间切，两日各 10 分钟，和等于 20 分钟；不再用 23:59:59.999。
- 极短亮屏、极短前台、同包多 Activity、超 6 小时截断、未结束区间、3 秒内连击解锁、排名同分、第 15 名边界，各有明确期望。
- 排名只对同一过滤集合计算；同分按包名升序；第 15 名不并列扩展。
- 系统数字健康降为真机对照，不当唯一正确值。
- 用机时长 60 秒改为「先测三天偏差再决定是否保留」，V6 与第 12 节使用同一容差。
- 耗电基线改成可执行的两天对照：第一天 `collect_enabled=false`，第二天全量采集；两天亮屏差超过 30 分钟就重测。

### 复核未编号项：客户端可以直接写表，绕过函数

复核在「对修改者新增判断的核对」末尾点了三件事，其中一件是「直接表写入绕开函数」。查下来确实开着口子：001 给 `location_points`、`daily_usage`、`app_usage`、`user_status` 都留了写自己的策略，后三张还是 `for all`。后果有三条：

- 纯查看模式只挡了函数，客户端直接 INSERT 仍然写得进，V20 的「不产生任何数据」不成立。
- `daily_usage` 直写可以绕过 `captured_at` 版本比较，N05 的原子性白做。
- 批量上限与字段校验全部失效。

改法：

- 删掉四张表的写策略，重建只读自己的 SELECT 策略。
- 再从 `authenticated` 与 `anon` 收回 INSERT / UPDATE / DELETE 权限。只靠 RLS 时 UPDATE 会静默匹配 0 行，客户端看不出没写成；收回权限后直接报 42501。
- 上报与设置函数是 SECURITY DEFINER，走属主权限，不受影响。

本机结果：用 A 的身份直写四张表都报 `permission denied for table ...`；自己读自己的行仍然正常；两个上报函数照常工作。校验查询新增 `write_closed`，策略与表级授权都为空才算过。

## 003 相对复核方跑过的版本改了什么

复核方跑的是 `0295766` 里的 003。之后改动如下，重跑前请以当前文件为准：

1. `report_locations` 与 `get_status` 改签名前先 `drop function`，修 42P13。
2. `presence` 增加 `resumed_at`，并对已存在的表做 `add column if not exists`。

4. 新增 `settings.collect_enabled` 与 `set_collect_enabled`，两个上报函数在关闭时抛 `collect_disabled`。

## 本机验证的方式与边界

用 PGlite 0.5.11，从空库依次执行 `001-schema.sql`、`002-contract.sql`、`003-hardening.sql`。环境补了 `auth.users`、`auth.uid()`、`authenticated` 角色、表级授权和 `supabase_realtime` 发布，模拟 Supabase 的公开表访问；表级授权在跑 003 之前给，并用 `alter default privileges` 让 003 新建的表也自动带上授权，和线上默认权限的顺序一致。

脚本是 `docs/verify-003.mjs`，结果落在 `docs/verify-003-results.json`：

```
mkdir /tmp/verify-003 && cd /tmp/verify-003
bun add @electric-sql/pglite
cp <repo>/docs/*.sql <repo>/docs/verify-003.mjs .
bun verify-003.mjs
```

本次结果 **31 项断言全 PASS**，覆盖 N01–N07、V13、V20、函数签名、四张表直写被拒，以及 003 自带校验查询的七行。任何人拿到这三个 SQL 都能复现，不需要我的机器。三次复核后又扩到 37 项，见 `docs/三次复核处理-2026-10-26.md`。

创建 A、B、C、D 四个账号，A 与 B 配对，使用合成坐标和用机数据。所有读取都 `set local role authenticated` 后执行，不是在超级用户下看结果。

**能证明的**：SQL 在干净库上可执行；四张原表对对象不可读、对本人只可读不可写；暂停与恢复的遮蔽（含恢复前采集、恢复后补传的点）；积压更旧的点不回退状态；未配对与陌生人被拒；presence 只有本人与对象可读；成员表不能伪造；发布集合只有 `presence`；新用户 presence；纯查看拒绝上报；顺序旧快照拒绝；003 自带的七行校验全为真。

**不能证明的**：

- 线上 Supabase 的表授权与本地模拟是否完全一致。
- Realtime 实际投递与消息体字段。
- 两个独立连接的并发快照写入。
- 真机时钟偏移对 `recorded_at` 与 `resumed_at` 比较的影响。
- pg_cron 是否真的每天跑。

这五项都列进了线上校验清单。
