这样做的另一个原因：原策略用「查不到 user_status 就当成没暂停」的否定子查询，收回读权限后反而让暂停失效。把入口收成一个函数，这类反噬就没有了。

05权限不变量

七条不变量在数据库层强制，界面判断只作展示优化。违反任何一条算缺陷，不算体验问题。

编号不变量强制在哪
I1未配对的账号读不到任何他人的行RLS 依赖 my_partner_id()，无关系时返回 null，条件恒假
I2可见性由数据主人决定，不由读者决定判据读的是对方的 settings，不是自己的
I3暂停覆盖全部三类get_status 与 get_usage 先判 paused_until，四张原表不对对象开放
I4写入只能落在自己名下，且只能走函数上报与设置函数内强制 user_id = auth.uid()；四张数据表对 authenticated 没有 INSERT / UPDATE / DELETE 权限，直写直接报 42501
I5对外只有两个读入口对象对四张原表没有任何 SELECT 策略，只能走 get_status 与 get_usage
I6订阅消息里不含敏感字段发布集合只有 presence，该表无坐标无电量；该表的行只有本人与对象读得到
I7纯查看设备不产生任何数据collect_enabled = false 时，两个上报函数直接抛 collect_disabled；直写表也被权限挡住，绕不过去
表读自己写自己读对象写对象
profiles是仅 nickname、avatar_url 两列，列级授权强制是否
couples是否，只走函数是否
couple_members是否，只走函数是否
devices是是否否
pair_codes是否，只走函数否否
location_points是否，只走 report_locations否，当前点只走 get_status否
daily_usage是否，只走 report_usage否，只走 get_usage否
app_usage是否，只走 report_usage否，只走 get_usage否
user_status是否，只走上报与设置函数否，只能走 get_status否
presence是否，写权限已收回；刷新信号由上报与设置函数维护是，无敏感字段否
settings是否，写权限已收回；只能走 set_sharing / set_collect_enabled是，只含开关布尔值否

错误形状

PostgREST 统一返回 {"code", "message", "details", "hint"}。自定义异常抛在 message 里。

message触发条件客户端处理
not_authenticated没有有效 JWT跳登录，清本地 token
not_allowed请求的 user_id 既不是自己也不是对象回落读对象，不重试
invalid_payload必要字段缺失或类型不对记日志丢弃，不重试
batch_too_large位置超过 50 点，应用超过 20 行拆包重发
invalid_code码不存在、已用、已过期提示重新输入，不清输入框
cannot_pair_self输了自己的码提示换对方的码
already_paired自己已有关系刷新进主页
partner_already_paired对方已有关系提示让对方先解绑
collect_disabled本机是纯查看模式却调用上报停掉上报循环，不改共享开关

HTTP 状态码不作业务判定依据。网络层先看 message，取不到再按状态码分类。

改函数签名必须先删

Postgres 不允许 create or replace 改返回类型。003 里 report_locations 从 int 改成 jsonb、get_status 增加一列，都先 drop function if exists 再建。后续迁移照此办理，否则报 42P13。

07上报契约

项约定
通道HTTPS 调 /rest/v1/rpc/，带 apikey 与用户 JWT
位置发送每个采样点立即发送。队列只在发送失败时攒批，不设「等 30 秒再发」
位置批量断网恢复后的补传单次最多 50 点，超过拆分
用机频次每 15 分钟一次，另在次日 00:05 补一次前一日终态快照
用机语义全量快照，服务端整日替换；请求必须带 captured_at，它是唯一版本号；p_apps 必须显式传数组，null 被拒，超 20 行在本地取 Top 20 后整体发
纯查看设备collect_enabled = false 时服务端直接拒绝上报，客户端不应起采集与上报循环。这只停上报，不改三类共享；旧数据是否可见仍由 share_* 决定
写入通道只能调两个上报函数与四个设置函数。四张数据表、settings、presence 对 authenticated 都没有写权限，直接 INSERT / UPDATE 报 42501，绕不过 collect_disabled 与版本比较；profiles 只给 nickname、avatar_url 两列更新权；devices 是唯一允许本人整行直写的表（004）
成功判据HTTP 2xx 且返回的 received 等于提交条数。不看 inserted，重发时它是 0
幂等位置靠 user_id + recorded_at；用机靠 captured_at，同版本重发是幂等成功
时钟启动时与每小时各校一次，用响应头 Date 减本机时间得偏移
乱序位置按 recorded_at 合并，旧点不覆盖当前状态；用机旧快照返回 -1 并丢弃，比较与写入在同一条 UPSERT 里完成

08实时订阅

项约定
订阅表只订 presence，按 user_id=eq.对方id 过滤。发布集合里只有这一张表
事件用途只当「该刷新了」的信号，收到后调 get_status 与 get_usage
消息内容user_id、online、last_report_at、resumed_at、updated_at，不含坐标与电量
新用户注册触发器就建 presence 行，首次定位前切换暂停或开关也能发出信号
谁能订presence 自己带 RLS：本人与对象读得到，未配对账号读到空集。不是靠客户端只订自己的行来挡
前台保持连接，另加 30 秒兜底轮询
后台断开订阅，退化 15 分钟轮询
断线判定30 秒无任何消息
重连退避 2、4、8、16、30 秒；成功后立即全量拉一次
失败降级连不上不影响展示，由轮询驱动

订阅不存在「收到即渲染」的路径。消息里根本没有坐标，坐标只能从 get_status 来，而那个函数会按 I2、I3 遮蔽。这一条是结构上的，不是约定上的。

09采集口径

指标数据源算法边界
亮屏时长 screen_on_ms UsageEvents 的 SCREEN_INTERACTIVE 与 SCREEN_NON_INTERACTIVE 按事件配对累加；查询时屏仍亮，从最后一次亮屏补到查询时刻 跨零点按半开区间 [当日 00:00, 次日 00:00) 切分，两侧相加正好等于总时长；短于 2 秒的配对记 0；单日上限 24 小时
应用前台 foreground_ms ACTIVITY_RESUMED 与 ACTIVITY_PAUSED 同一包连续 RESUME 只保留最外层，按包累加 短于 1 秒记 0；单段超过 6 小时截断并记异常；多 Activity 同包只算最外层；查询时仍未结束的区间补到查询时刻；排除 com.couplesee 自身
应用排行 上一条结果 只对同一过滤集合（前台满 60 秒、已排除本 App）按 foreground_ms 降序取前 20 前台不足 60 秒不上报；时长相同按包名升序；第 15 名同分时只取一个，不并列扩展；界面只展示前 15
解锁次数 KEYGUARD_HIDDEN 按本地日计数 3 秒内连续多条合并为一次
锁屏次数 KEYGUARD_SHOWN 按本地日计数 同上
首次与末次解锁 同解锁事件 当日最早与最晚的一条 当天无解锁则都为 null。只表示解锁，不表示之后停止使用
定位回调 高德定位 SDK，高精度模式 移动 3 秒一次，静止 20 秒一次 精度差于 200 米丢弃；速度大于 60 米每秒丢弃
入队与上报 定位回调结果 移动 30 秒取一点、静止 5 分钟取一点，取到即发 队列只在失败时生长

11状态与新鲜度

首页永远处于下面九种状态之一。判定从高到低，命中即停。

序状态判定展示
1未配对无 couple_members 行配对引导，不给地图
2读取失败请求异常且无本地缓存「暂时读不到」加重试，不显示上次的旧数据
3暂停中paused_until 大于响应里的 server_now 且非哨兵「已暂停，HH:mm 恢复」，三类数据都不显示
4手动暂停paused_until 等于哨兵「已暂停共享」，三类都不显示
5无数据last_report_at 为 null「对方还没开始上报」
6实时年龄不超过 1 分钟绿点，时间写「刚刚」
7延迟1 到 10 分钟「N 分钟前」，分钟数取整到分钟
8过期10 分钟到 2 小时头像转灰，仍显示最后位置与时点

年龄的定义是 响应里的 server_now 减 last_report_at，不用客户端时钟。暂停与关闭共享同时成立时，第 3、4 条优先，因为暂停是更明确的意图。

恢复后的旧点遮蔽在服务端完成，不靠客户端记状态。手动恢复写 presence.resumed_at，get_status 把早于它的点一律返回 null；定时暂停到期则用 paused_until 与最后一点的采集时刻比较。新打开的查看端与服务端算出的结果一致。

场景规则
在线暂停先调 set_pause，成功后停采集。顺序不能反
断网暂停本地立即停采集并置暂停标志，界面写「正在同步暂停」，联网后补 set_pause，成功才撤提示
有积压队列时暂停队列保留但不再发送；恢复共享后按 recorded_at 正序补传，早于恢复时刻的点由服务端遮蔽
暂停期间的数据不采集、不上报。恢复后不补采暂停那段时间
定时恢复paused_until 到期即自动恢复采集，不依赖本地闹钟，进程重启也成立
暂停不改点时间set_pause 只写 paused_until，不改 user_status.updated_at。这一点写错会让恢复后的旧点被当成新点
恢复后展示服务端在拿到新点之前返回 null，界面显示「已恢复，正在定位」，不显示暂停前的旧坐标

R04 结论

v0.1 用两台安卓。她的真我 GT8 采集全部数据并查看；你的备用机只作查看端，关闭自身三类共享并把 collect_enabled 设为 false，不上报位置、电量与用机。

备用机系统已确认为最新 Android（不低于 9），minSdk 保持 28，三项用机指标不需要降级。

备用机关闭共享的原因是位置诚实：那台机不随身，开着共享会让对方看到一个人停在某处不动，比看不到更误导。等 iOS 端上线再打开。

关闭采集不是只靠界面约束：服务端在 collect_enabled = false 时直接拒绝两个上报函数，队列里残留的旧点也传不上去。

进入纯查看模式是两步，不是一步。先关采集，再关三类共享。官方理由是位置诚实：先停上报，避免在关共享的瞬间还有新点落库；反过来先关共享、后关采集，中间那段时间对方看不到，但本机仍在产生数据，属于白采集。

两步都成功才算进入纯查看模式。界面一键操作时按上面顺序串行执行；第二步失败就停在「部分完成：已停止采集，仍在共享」，并留一个只重试第二步的按钮。不要回滚第一步，也不要把两步合成一个服务端函数——set_collect_enabled 与 set_sharing 各自幂等，重试只补没成的那一步即可。

这也解释了为什么 V20 与 V21 分开验：只关采集时对方仍看得到旧数据，是设计行为；两步都做完才要求看不到。把两件事写进同一条验收，会逼着实现去改接口语义。

这条同时解决 PRD 验收第 1 条：两台真机注册配对即可完成。
