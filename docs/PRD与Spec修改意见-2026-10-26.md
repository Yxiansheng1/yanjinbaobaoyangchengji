## R01 共享权限存在绕过路径

**位置**：Spec 第 5、8 节，约第 294、327、428、441 行；`001-schema.sql` 第 365–372 行；`002-contract.sql` 第 192–211 行。

**问题**：Spec 要求客户端读取 `visible_status`，但原表 `user_status` 仍允许对象读取整行，Realtime 也订阅原表。客户端不渲染消息中的坐标，不能阻止消息接收方取得坐标。视图中的 `lat`、`lng`、`accuracy` 只判断暂停，没有判断 `share_location=false`。因此，即使只读取视图，关闭位置共享也不能隐藏经纬度。

**修改建议**：

- 在服务端限制所有读取路径，包括原表、视图、RPC 和实时消息；不能只约定客户端读哪个入口。
- 为经纬度、精度、地名统一执行位置共享规则；为电量和充电状态执行电量共享规则。
- 采用受控查询接口、拆分敏感表与公开状态表等方案时，明确调用者身份校验和底层权限。当前视图使用 `security_invoker=true`，不能只撤销原表权限而不验证视图是否还能工作。
- 先定义暂停影响的数据类别，再统一各入口。

**验收要求**：

- 已配对的 B 在 A 暂停或关闭位置共享后，不能通过任何开放入口获得 A 的坐标、精度或地名。
- 检查实际 Realtime 消息体，不能只检查页面是否隐藏。
- 关闭电量共享后，原表、视图及消息均不能暴露电量和充电状态。
- 保留未配对账号的隔离测试。现有 V11 仅覆盖未配对账号，不能代替上述测试。

参考：[Supabase Postgres Changes](https://supabase.com/docs/guides/realtime/postgres-changes)、[Supabase Views](https://supabase.com/docs/guides/database/views)。

## R02 配对规则未被完整保证

**位置**：Spec 第 4、6 节，约第 230、334 行；`001-schema.sql` 第 29–30、174–259 行。

**问题**：`user_a`、`user_b` 各自唯一，不能保证同一用户在两列合计只出现一次。并发创建 `(A,B)` 和 `(B,C)` 时，两组索引都不冲突；函数只锁配对码，两个请求可能在另一段关系提交前都通过检查。`my_partner_id()` 使用 `limit 1`，无法解决多段关系造成的歧义。

此外，Spec 承诺生成新码会作废旧码，但生成函数没有按用户作废旧码。

**修改建议**：采用可跨角色保证唯一性的关系模型，或对参与配对的双方用户按固定顺序加事务锁，并在锁内重查关系。补齐新码使旧码失效的事务语义。

**验收要求**：

- 并发执行 B 接受 A 的码、C 接受 B 的码，B 最多只能进入一段有效关系。
- 同一码并发接受时只允许一次成功，并明确失败返回。
- 同一用户生成第二个码后，第一个码不可再接受。
- 正常配对后，双方查询到的对象关系一致。

## R03 快照重试会导致数据倒退

**位置**：Spec 第 7 节，约第 370–374 行；`002-contract.sql` 第 138–177 行。

**问题**：`report_usage` 无条件替换当天数据，没有采集截止时间或版本。10:00 的失败请求在 10:15 快照之后重试，会覆盖较新的屏幕时间和应用排行。服务端还将 `updated_at` 写为当前时间，旧数据会被显示成刚更新。

**修改建议**：请求增加快照版本或采集截止时间。服务端在同一事务内判断版本，并统一接受或拒绝日汇总与应用列表。区分数据采集时间和服务器接收时间。整日替换只能避免重复累加，不能处理乱序。

**验收要求**：先发送新快照，再发送旧快照，最终数据保持新版；重复发送同一快照不改变结果；日汇总与应用列表不能来自不同版本。

## R04 v0.1 缺少实际用户的查看端

**位置**：PRD 第 3、11 节，约第 202、527–533 行；Spec 第 2、15 节，约第 180、662 行。

**问题**：实际用户是一人安卓、一人 iPhone，PRD 验收要求他打开 App 查看她的数据。Spec 排除了 iOS，又没有定义其他查看端。两台安卓能完成技术验证，但不能证明两位实际用户可以每天使用。

**待定选项**：

- 将 v0.1 明确命名为安卓技术验证版，调整目标用户、测试设备和交付承诺。
- 增加 iPhone 可访问的最小查看端，明确它是否只查看数据、是否采集自身数据，以及配对流程。

**验收要求**：发布范围、真实设备组合和验收脚本一致。若保留日常使用目标，必须说明 iPhone 用户从哪里登录、配对和查看。

## R05 位置更新指标互相冲突

**位置**：Spec 第 2、7、9、12 节，约第 176、368、489、579–581 行。

**问题**：移动时每 30 秒采样，队列又允许等待 30 秒才发送，却要求端到端 P95 不超过 10 秒。即使从采集完成开始计时，队列等待也可能超过指标。

SDK 同时被要求每秒高精度定位，只是按移动状态决定是否入队。这属于减少保存或上传次数，不能据此证明定位本身已经降频省电。

**修改建议**：分别定义定位周期、有效点采样周期、发送等待、网络传输延迟和页面数据年龄。给每个指标写明起止时刻、前后台条件、网络条件及分位数。根据真机结果选择 SDK 工作方式，并同步耗电目标。

**验收要求**：用同一组时间戳分别计算上述指标；确认队列策略不会必然违反延迟上限。耗电测试写明设备、系统版本、移动与静止时间、网络、基线测法，以及“8%”的计算方式。

## R06 暂停和退出规则不完整

**位置**：PRD 第 4、5、6 节，约第 221、306、383–390 行；Spec 第 5、11 节，约第 306、564–571 行。

**问题**：权限不变量写暂停优先于一切共享开关，状态表却写用机数据照常。实际行为更接近暂停位置共享。断网点暂停、尚未发送的队列、在途请求、定时恢复及恢复时的旧坐标展示均缺少完整规则。解绑安排在 v0.4，也与允许用户退出共享的原则不一致。

**修改建议**：

- 明确暂停覆盖位置、用机、电量中的哪些类别，名称和界面提示与实际行为一致。
- 定义断网时本地停止采集的时点、服务器尚未确认的提示，以及恢复网络后的同步顺序。
- 定义暂停前排队数据、在途请求、暂停期间数据的处理方式。
- 定义定时恢复、进程退出后重启恢复及取得新坐标前的展示规则。
- 建议将单方解除共享关系纳入最小版本；关系结束后停止对方读取，并明确历史数据的保留与删除范围。

**验收要求**：覆盖在线暂停、断网暂停、有积压队列时暂停、手动恢复、定时恢复、重启后恢复及退出关系。不能把尚未同步服务器的暂停显示为对方已不可读取。

## R07 无数据状态无法命中

**位置**：Spec 第 11 节，约第 559–565 行；`001-schema.sql` 第 104–115、163–164 行。

**问题**：Spec 用 `updated_at=null` 判断没有数据，但 SQL 将其设为非空、默认当前时间，并在注册时创建状态行。用户从未上传位置，也可能显示为实时。五分钟内统一显示刚刚，还会把四分多钟前的数据显示成刚更新，与按真实时间展示的约定不一致。

**修改建议**：单独记录有效采集时间或数据存在标志。将数据新鲜度、共享状态和连接状态分开定义，补齐关闭共享、无权限、读取失败等情况的优先级。

**验收要求**：刚注册且未采集的用户显示无数据；超过一分钟的数据能显示准确年龄；暂停、关闭共享和过期同时发生时，页面按明确优先级显示。

## R08 末次解锁不代表放下手机

**位置**：PRD 第 6 节 B5，约第 409–414 行。

**问题**：`KEYGUARD_HIDDEN` 表示解锁。23:00 解锁后使用到次日 01:00，不能展示为 23:00 最后一次放下手机，也不能据此认定已经睡觉。

**修改建议**：直接展示最后解锁时间。若需要表示停止使用，另定义锁屏或最后交互指标及适用限制。

**验收要求**：用跨午夜连续使用的事件序列检查文案，解锁、锁屏和睡眠推断不得混用。

## R09 常去点需求尚未冻结

**位置**：PRD 第 6、12 节，约第 363–368、553 行；Spec W-16，约第 611 行。

**问题**：PRD 要求聚类形成家、公司等候选点，并支持双方命名、删除。Spec 只有逆地理编码和一张工单，没有地点数据结构、归属、编辑权限、聚类规则或删除后行为。PRD 文末仍把是否保留该功能列为待确认。

**待定选项**：v0.1 只显示逆地理编码地址；或保留常去点并补齐契约。不能将两种范围都留给实施人员自行解释。

**验收要求**：若保留，定义重复出现的次数与天数、距离计算、候选生成、命名冲突、删除后是否重新生成、位置共享关闭后的可见性。若延期，同步删除相关页面与工单承诺。

## R10 最低系统版本与事件来源不匹配

**位置**：Spec 第 2、9 节，约第 178、451–479 行。

**问题**：最低版本为 API 26，但亮屏及锁屏、解锁统计依赖的 `SCREEN_INTERACTIVE`、`SCREEN_NON_INTERACTIVE`、`KEYGUARD_HIDDEN`、`KEYGUARD_SHOWN` 在 API 28 才加入。文档只为应用前台事件写了旧版分支，未说明这些指标在 API 26–27 如何采集。

**修改建议**：提高最低版本，或明确 API 26–27 的替代来源和能力降级。目标真机版本较新，不代表声明支持的旧版本自动成立。

**验收要求**：最低版本设备能够按声明提供指标；不能提供的指标显示不支持，不得显示为零。版本范围同步到 PRD、构建配置和安装说明。

参考：[Android API 28 事件变更](https://developer.android.com/sdk/api_diff/28/changes/android.app.usage.UsageEvents.Event)。

## R11 验收口径不足以判断正确性

**位置**：Spec 第 9、12、14 节，约第 455–467、582–584、643–649 行；`002-contract.sql` 第 61–63 行。

**问题**：V6 用系统数字健康验证自定义统计，却未证明双方口径一致。Spec 过滤短时段、截断超过六小时的应用区间，可能主动产生偏差。时长误差不超过 60 秒也不能评价 Top 15 排名是否正确。

补传只比行数，不能证明每个具体点都正确到达。若服务端已提交而响应丢失，重试会返回新增零行，契约尚未说明客户端如何确认成功并清队列。

**修改建议**：

- 用固定事件序列验证亮屏、解锁、应用前台及日切；系统数字健康只作明确口径后的对照。
- 分别定义时长误差、首末事件时间和排名集合的验收条件。
- 按位置点幂等键及必要字段对账，区分接受成功与新增行数。
- 定义整批失败、单点无效、响应丢失和重复提交时的队列处理。

**验收要求**：覆盖跨午夜、查询时仍亮屏、短时段、长时段、重复快照、旧快照、重复位置点及响应丢失。完整率的分母和允许丢弃的规则须明确。
