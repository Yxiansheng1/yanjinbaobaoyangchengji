## E01 校验通过后仍按原始文本转换整数

优先级：P2。属于 D01 同一根因的剩余部分，本地已复现。

位置：`005-contract-fix2.sql:97、128、149、302–305、342–343`；契约 `:302–303、479–480`。

005 先将数值转成 numeric，并用 `v = trunc(v)` 判断整数性。数值为整数但带小数形式的 JSON，例如 66.0、1000.0、3.0，会通过这一步。随后电量和应用明细又从原始文本直接转换为 smallint、bigint、int，产生 22P02。

| 原始 JSON 输入 | 实际结果 |
| --- | --- |
| 位置点 battery: 66.0 | 22P02，smallint 无法直接解析文本 66.0 |
| 应用 foreground_ms: 1000.0 | 22P02，bigint 无法直接解析文本 1000.0 |
| 应用 launch_count: 3.0 | 22P02，int 无法直接解析文本 3.0 |
| 日汇总 screen_on_ms: 1000.0、unlock_count: 3.0 | 成功，因为该路径使用已经校验的 numeric 变量转换 |

这不是用户把数值写成 JSON 字符串。输入仍为 JSON number，而且已经通过现有整数性判断。同类字段因转换路径不同而产生不同结果。若产品选择拒绝带小数形式的整数，也应明确返回 invalid_payload，不能先通过检查再漏出原生错误。

影响范围：按契约使用 Short、Int、Long 正常序列化的客户端通常发送 66、1000、3，不会触发此问题；通用 JSON 构造器或其他调用者保留小数形式时可能触发。未发现跨账号访问影响，也没有证据表明失败会部分写入。无需提升为安全漏洞或结构重做。

建议沿用现有“按数值判断整数”的规则，在已有整数性与范围校验后，经 numeric 转成目标类型：

```sql
-- 位置历史和当前状态两处 battery 都处理
nullif(e ->> 'battery', '')::numeric::smallint
nullif(v_last ->> 'battery', '')::numeric::smallint

-- 应用明细两列
coalesce((e ->> 'foreground_ms')::numeric::bigint, 0)
coalesce((e ->> 'launch_count')::numeric::int, 0)
```

必须保留前面的整数性和范围检查，避免真正的非整数被转换时舍入。005 已有上线记录，应通过后续迁移修正，不覆盖已执行的历史文件。
