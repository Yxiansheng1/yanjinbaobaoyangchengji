# 情侣看看契约 schema 审查意见

审查日期：2026-10-26。基线提交：`65e80b8`。

对象：`情侣看看-契约-schema-v0.1.html`，对照 SQL 001、002、003 和规格 v0.1.5。读者为负责客户端接口、数据库契约和文档的人员。

结论：新契约不能直接视为 SQL 的准确镜像。存在会清空应用明细的参数语义错误，以及整日快照被错误拆包的处理建议；时间字段、可写范围、错误形状和维护函数授权也有偏差。上一轮已经验证的主要对象隔离修复没有因此被推翻，本次问题集中在新契约和剩余 SQL 行为。

## 验证范围

在本地 PGlite 0.5.11 空库依次执行三份 SQL，模拟 Auth、authenticated、anon 角色，并在执行 003 前配置普通表授权。测试使用合成账号和数据，没有连接线上 Supabase，没有修改项目 SQL。

SQL 003 SHA256：`4357639D18D183985EAC7B3782AF69EC5BE71F02EB6754B7CFE235D4ADB35623`。

结果文件：`契约schema审查-本地验证结果.json`。复现脚本：`verify-contract-schema.mjs`。结果记录的是观察值与预期异常，不是全绿断言列表。

## C01 null 应用列表实际会清空明细

**优先级：高。本地已复现。**

位置：契约第 342 行；`003-hardening.sql` 第 695–697 行。

契约写 `p_apps=null` 表示不动应用明细，`[]` 才清空。SQL 却先无条件删除当天全部应用行，再判断是否需要插入，因此 SQL NULL 与空数组都会清空。

复现：先上传 `original.app`，再以更晚版本上传 `p_apps=null`，应用行由 1 行变成 0 行。

修改选择：

- 保持目前整日全量替换语义：将文档改成 null 和空数组均清空；更建议要求显式数组，防止客户端意外漏传或错误置空。
- 若确实需要 null 保留：调整 SQL，将删除和插入放入非 null 分支，并明确日汇总已更新、应用仍为旧快照时如何标示各自采集时间。

不能只移动 DELETE 而不说明快照一致性。当前 `captured_at` 是整个日报版本，保留旧应用列表会引入混合版本。

验收：分别测试非空数组、空数组、SQL NULL、JSON null、缺省参数，写明每种输入是接受、拒绝、清空还是保留。

## C02 应用快照不能按位置批次拆包

**优先级：高。本地已复现。**

位置：契约第 389 行；`003-hardening.sql` 第 662–663、679–697 行。

错误表将位置超过 50 点和应用超过 20 行统一处理为拆包重发。位置点逐条追加，可以拆包；应用是整日替换，每包都会覆盖上一包。

复现：21 个应用被拒后，按文档拆成 20 个和 1 个，以相同日期、相同版本分别发送。两次均接受，最终只剩最后一包的 `app.20`。

修改要求：将错误处理分开。位置超过上限时拆批；应用超过上限时按统一排名规则取 Top 20，整体发送一个快照。若要支持分页提交，必须另设计服务端提交协议，不能沿用当前 RPC。

验收：构造 21 个应用，客户端保留正确的前 20 名；服务端最终列表不能变成最后一包。

## C03 清理函数没有落实任务专用权限

**优先级：高。本地默认授权环境已复现，线上授权待核验。**

位置：契约第 295 行；`001-schema.sql` 第 262–269 行及函数授权段。

文档写 `purge_old_locations()` 只给定时任务使用，但实现为 SECURITY DEFINER，没有调用者检查，也没有撤销 PUBLIC 执行权限。当前项目脚本未将它限制到任务角色。

本地结果：anon 和 authenticated 的函数执行权限均为 true。匿名角色调用成功，并删除另一合成账号超过 7 天的位置点。影响范围限定于函数条件匹配的旧位置点，不是任意数据删除；但调用权限明显宽于契约描述。

修改要求：从 PUBLIC、anon、authenticated 撤销该维护函数的执行权限，仅保留实际任务执行角色或属主。确认定时清理使用的角色仍然可执行。客户端调用列表应将维护函数单列。

验收：匿名和普通登录身份调用被拒，定时任务身份执行成功；核对线上实际 ACL，不仅检查是否存在某条显式 GRANT。

依据：[PostgreSQL 默认函数 EXECUTE 权限](https://www.postgresql.org/docs/18/ddl-priv.html)、[Supabase 数据库函数权限说明](https://supabase.com/docs/guides/database/functions)。

## C04 状态接口的 updated_at 含义写错

**优先级：中。本地已复现。**

位置：契约第 262 行；`003-hardening.sql` 第 419–420 行。

文档把 `get_status.updated_at` 写成最后一点的采集时刻，SQL 实际返回 `coalesce(presence.updated_at, user_status.updated_at)`。正常有 presence 行时，改共享开关、暂停和心跳都会推进该时间，即使没有新位置。

本地结果：同一个状态响应的 `last_report_at` 保持原采集时刻，执行 `set_sharing` 后 `updated_at` 已变化。

修改要求：将返回字段说明改为状态或刷新信号更新时间。位置采集时间和数据年龄使用 `last_report_at`。分别说明原表 `user_status.updated_at` 与 RPC 同名字段的含义，不能因为同名就当成同一数据来源。

验收：只有设置变化而没有定位时，采集时间不变，状态更新时间推进。

## C05 文档的可写范围未被数据库强制

**优先级：中。本地已复现。**

位置：契约第 67、72、77、82 行；`001-schema.sql` 的 profiles、settings 策略；`003-hardening.sql` 第 213–215 行。

| 文档表述 | 当前本地数据库行为 |
| --- | --- |
| 写全部走函数 | devices、profiles、settings、presence 仍有直接写入路径 |
| settings 不能直写 | 普通用户可以直接 UPDATE 自己的共享开关 |
| presence 只能写心跳列 | 普通用户可以直接改自己的 resumed_at，不仅 updated_at |
| profiles 只能改昵称头像 | 普通用户可以改自己的 email、created_at |

这些操作仍限定在本人行，本次没有发现由此直接修改他人行。问题是文档把客户端约定写成了数据库限制。直接修改 settings 还不会执行设置函数中的 presence 刷新逻辑。

修改要求：区分允许客户端使用的接口与数据库实际强制权限。若要禁止直写，撤销对应表级权限并提供受控函数；若只允许修改指定列，配置列级授权或函数接口，保留宽泛的表级 UPDATE 权限无法实现该限制。

验收：逐表用本人身份验证允许与禁止的列，并检查直接表更新、删除是否符合约定。

## C06 错误形状和字段范围没有完整契约

**优先级：中。本地已复现。**

位置：契约第 323、388、489、505 行；两个上报函数的输入处理；位置与用机表约束。

缺字段或类型错误并不统一返回 `invalid_payload`：

| 输入 | 实际结果 |
| --- | --- |
| 位置点缺 lng | SQLSTATE 23502，非空约束错误 |
| lat 为字符串 bad | SQLSTATE 22P02，类型转换错误 |
| lat=999、lng=999、battery=150、accuracy=-5 | 接受并写入 |
| screen_on_ms=-100、unlock_count=-2 | 接受并写入 |
| captured_at 为 2099 年 | 接受；之后该日期的正常版本返回 -1 |

未来版本的风险在文档中已经提到，但仅写客户端不能这样做，不能防止设备时钟、校时或序列化错误。错误坐标和负统计值同样缺少数据库约束。

修改要求：

- 明确必填、可缺、省略默认、SQL NULL 和 JSON null 的差异。
- 对坐标范围、电量 0–100、非负时长与计数增加适当验证。
- 设定并明确允许的未来时钟偏差，同时保留历史补传能力；不要用一个未经测量的固定偏差代替产品决定。
- 选择稳定错误协议：在函数内转换为约定业务错误，或在文档列出可出现的 SQLSTATE 和客户端处理。不能只列 `invalid_payload`。
- 对同批无效点说明整批原子失败、如何定位问题点，以及哪些数据可以重试。

验收：边界值、越界、缺失、错误类型、未来时间及恢复后正常上报均需覆盖。

## C07 分列唯一索引的错误说明被重新写入

**优先级：中。文档错误，当前配对实现未因此退回旧版。**

位置：契约第 118 行。

文档称 user_a、user_b 各自有 active 部分唯一索引，所以一人只能有一段关系。两列各自唯一不能阻止同一用户在两行中分别位于不同列。这正是前两轮已处理的问题。

当前实现依靠 `couple_members.user_id` 主键、受控配对写入、双方锁和成员校验共同保证正常配对路径。文档应描述实际机制，不把保证归因于旧索引。

验收：检查文字与当前 SQL 一致，保留既有交叉并发配对用例；此处不要求重新设计已经修复的关系模型。

## C08 时间字符串不能保证固定 Z 后缀

**优先级：中。数据库 JSON 输出已本地验证，HTTP 返回未实测。**

位置：契约第 401、468、487 行。

文档多处保证线上时间戳一律以 Z 结尾。SQL 的 timestamptz 存储时间点，并不保证这个字符串后缀。PostgreSQL 按会话时区序列化，本地 UTC 会话的 JSON 输出为 `2026-10-26T00:00:00+00:00`；其他时区可以带不同偏移。

修改要求：请求可统一发送 Z 格式；响应应接受有效 ISO-8601 偏移和小数秒，再归一化为 Instant。若业务坚持输出只能是 Z，必须增加并验证输出格式化层，不能只靠 timestamptz 类型。

当前 Kotlin DTO 使用 String 本身没有问题；风险在后续解析器或字符串比较，不应假设原示例就是唯一格式。

参考：[PostgREST PostgreSQL 类型与时区说明](https://postgrest.org/en/stable/how-tos/working-with-postgresql-data-types.html)。

参考：[PostgREST 函数 RPC 返回形状](https://docs.postgrest.org/en/stable/references/api/functions.html)。
