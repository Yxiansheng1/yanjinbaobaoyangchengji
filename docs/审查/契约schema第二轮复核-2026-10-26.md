日期：2026-10-26。基线：`d3f6970`。审查对象为契约 v0.2、SQL 001–004、规格 v1.6、004 验证脚本及线上执行记录。读者为负责契约定稿和后续客户端开发的人员。

## D01 校验错误仍未统一

优先级：P2。本地已复现。

位置：`004-contract-fix.sql:144–148、179、294–296、328–329、366–369`；契约 `:445、460–461`。

当前先检查 JSON number 和部分数值范围，再直接转换为 smallint、int、bigint 或 real。JSON number 可以是小数，也可能超过目标类型的容量，因此“校验类错误已经全部转成 invalid_payload”仍不成立。

| 输入 | 实际错误 |
| --- | --- |
| battery = 66.5 | 22P02，smallint 转换失败 |
| unlock_count = 1.5 | 22P02，integer 转换失败 |
| unlock_count = 2147483648 | 22003，integer 越界 |
| accuracy = 1e40 | 22003，real 越界 |
| 同一 p_apps 内两行 package_name 相同 | 21000，单条 UPSERT 不能重复更新同一行 |

影响：调用者会进入未知错误处理，无法按契约稳定识别无效载荷。重复包名案例已验证整个事务回滚，日汇总和应用明细不会部分写入；不能将此描述成半写或数据丢失。

修改建议：整数列检查整数性和存储范围，浮点列检查可存储范围；同批包名重复时明确拒绝或预先合并。对函数内部已知的输入错误返回 invalid_payload；发生在 RPC 参数绑定阶段的原生错误应另列处理规则，不承诺所有错误都能在函数内转换。无需捕获并伪装全部未知数据库异常。

验收：补齐以上案例；保留合法边界和整批失败回滚测试。客户端明确原生输入错误是否丢弃、提示或记录，避免无限重试。

## D02 新增 RPC 示例有三处错误

优先级：P2。SQL 行为已本地验证，HTTP 格式参照官方资料，线上 HTTP 尚未实测。

位置：契约 `:395、418–425、431`；`003-hardening.sql:380–385`。

1. “真实的 RPC 响应永远是数组”范围过大。默认响应下，get_status、get_usage 的表返回值是数组；report_usage 返回数字，report_locations 返回 JSON 对象，配对码返回字符串。当前后续示例本身就与这句总规则矛盾。
2. void RPC 示例写死 `200` 和 `Content-Length: 0`。PostgREST v13.0.4 的官方实现对 void 返回 `204`、空体；线上具体版本和网关响应头本轮未抓取。应把客户端规则写成接受约定的成功状态并跳过 JSON 解码，再用真实响应确定示例，不依赖固定 Content-Length 头。
3. get_status 示例写“p_user_id 指向不存在的人返回 []”。实际先检查访问权限：指定一个非本人、非对象的 UUID，得到 P0001 / not_allowed，即使该 UUID 不存在。只有未配对且不指定目标等情况才返回空集。应改文档，保留现有权限判断。

影响：按统一数组解码或只接受 200 编写网络层，会误判成功；按错误的空集示例处理无权访问，也会走错页面状态。

验收：用真实 JWT 分别记录表返回、标量、JSON 对象、void，以及未配对默认读取和指定无关 UUID 的状态码、响应体。保存脱敏结果，不保存 JWT。

依据：[PostgREST 函数返回形状](https://docs.postgrest.org/en/stable/references/api/functions.html#scalar-functions)、[PostgREST v13.0.4 Response.hs 的 void 分支](https://github.com/PostgREST/postgrest/blob/v13.0.4/src/PostgREST/Response.hs#L195-L201)。

## D03 用机上报没有产生订阅刷新信号

优先级：P2。本地已复现。属于既有实现遗漏，004 仍保留，并非本轮新引入。

位置：`004-contract-fix.sql:333–376`；契约 `:255、568`；规格 `:420–425`。

契约要求只订阅 presence，收到变化后重新读取 get_usage。report_usage 成功写入 daily_usage 和 app_usage 后直接返回，没有更新 presence，也没有相应触发器。

复现：记录 presence.updated_at，成功上传一条应用快照，返回 1；再次读取 presence.updated_at，值完全不变。因此这次用机更新本身不会产生 presence 表变化通知。

影响限定：规格已有前台 30 秒兜底轮询；后续位置上报也可能触发刷新。所以这里不是用机数据永远不可见，而是用机数据不能独立触发实时更新。

修改建议：接受新快照后，在同一事务内更新 presence.updated_at；不要因此改写表示位置采集时间的 last_report_at，也不要把旧版本返回 -1 当作新数据。若产品选择用机完全依靠轮询，也可以明确写进契约，避免承诺同一种订阅行为。

验收：在没有位置上报和设置变化的条件下，仅上传用机数据；确认选定的刷新方式能让查看端获取更新。Realtime 投递仍需真实环境验证，本地测试只证明表是否变化。

## D04 对称唯一索引不保证一人只有一段关系

优先级：P3。SQL 注释与验证用例表述问题，不是新发现的普通用户越权漏洞。

位置：`004-contract-fix.sql:52–56`；`verify-004.mjs` 的 C07 用例。

新索引阻止同一对人以 A–B、B–A 两种方向重复配对，但不能阻止不同组合 A–B、C–A。原单列索引加上新索引仍允许后一种组合。

本地管理员诊断：已有 A–B 时直接插入 C–A 成功。另一个普通 authenticated 配对 RPC 对照用例仍返回 partner_already_paired。二者证明的是不同层次，不能混为一谈。

修改建议：将“对称索引才真正约束住一人一段关系”改为“对称索引防同一对关系正反向重复；成员主键、受控写入和锁内检查保障正常配对路径”。保留现有成员模型，不需要为修正文案重新设计关系表。

原测试只证明同一对的反向插入被拒，不能用它替代不同对象的交叉配对测试。

## D05 时间格式说明没有改干净

优先级：P3。

位置：契约 `:472、539、558`。

第 539 行映射表仍写 timestamptz 在线上为“ISO-8601 带 Z”，与第 558 行“响应可能带任意偏移”冲突。统一改为“ISO-8601 时间戳，带 Z 或有效偏移”。

第 472 行称 Instant.parse 只接受 Z，表述过于绝对。Java 17 的 ISO_INSTANT 官方说明包含偏移解析与 UTC 转换。Android 最低版本的具体运行库本轮未验证，不能用桌面 JDK 行为代替手机兼容测试。可以继续采用 OffsetDateTime.parse(...).toInstant()，把理由写为统一接受偏移格式，并删除无版本限定的断言。

验收：目标 Android 运行环境接受 Z、+00:00、+08:00 和小数秒，等价输入得到同一时间点。

依据：[Java 17 ISO_INSTANT 文档](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/time/format/DateTimeFormatter.html#ISO_INSTANT)。

## D06 权限摘要和验证状态仍有冲突

优先级：P3。文档修正。

- 契约第 73 行仍写“写全部走函数”，第 78 行把 profiles 客户端写标为“否”，但实际允许本人直接更新 nickname、avatar_url；devices 也允许本人直接写。将摘要和表格统一为准确边界。
- 规格第 296 行仍写 presence 可由客户端写心跳；004 已撤销写权限。应同步改为上报和设置函数维护，客户端不可直写。第 297 行 settings 的“是”也应说明仅经 RPC 更新。
- 契约第 61 行声称写权限、校验、错误码和唯一索引“现在都是线上真实行为”；下一行以及线上校验记录第 48–49 行又明确行为、函数体未独立核验。七项权限和索引查询不足以证明全部返回值与校验规则。

修改建议：保留“004 已部署，权限与索引结构核对通过”，把具体行为标为本地验证或待真实 JWT 验证。线上执行记录可以作为部署证据，不扩张成所有接口行为已验证。
