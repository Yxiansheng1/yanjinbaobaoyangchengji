# 情侣看看 PRD 与 Spec 二次复核

复核日期：2026-10-26。代码基线：`0295766`。

读者：负责修改 PRD、Spec 和 SQL 的人员。本文同时核对原审查意见、修改结果，以及《我的意见》中的反驳。

结论：部分反驳成立，原审查需要收窄产品建议和指标要求。修改方向总体有效，但 003 仍有权限缺陷，不能据处理记录判定修复完成。本次在本地隔离数据库复现了关键问题，未连接或修改线上 Supabase。

## 原意见的更正

| 争议 | 二次判断 |

| R06 要求首版加入解绑 | 撤回作为必须修复项的判断。解除关系、停止共享、删除数据是不同操作。只要全部共享能由本人可靠地停止，首版延期解绑是可接受的产品取舍。原审查把设计原则推导为首版必须支持解绑，表述过强 |

## 本次验证范围

本地使用 PGlite 0.5.11，依次执行未经修改的 `001-schema.sql`、`002-contract.sql`、`003-hardening.sql`。测试环境提供 `auth.users`、`auth.uid()`、`authenticated` 角色和表级读写授权，模拟 Supabase 常见的公开表访问环境，保留项目原有 RLS 与函数实现。

创建 A、B、C、D 四个合成账号，A 与 B 正常配对，使用合成坐标及用机数据。没有使用线上账号、真实位置或密钥。

结果证明本地 SQL 行为；线上表授权可能不同，仍须用真实用户 JWT 复测。本次没有运行 Supabase Realtime 服务，也没有进行多连接并发实测。涉及并发的条目明确标为静态分析。

配套证据：`PRD与Spec二次复核-本地验证结果.json`。

## N01 未配对账号可读取指定用户状态

**级别：阻断。证据：本地复现。**

位置：`003-hardening.sql` 第 231–236 行。

```sql
if v_target <> v_uid and v_target <> public.my_partner_id() then
  raise exception 'not_allowed';
end if;
```

未配对时 `my_partner_id()` 返回 NULL。调用者指定其他用户 ID 后，条件得到 `TRUE AND NULL`，结果为 NULL；PL/pgSQL 的 IF 不执行拒绝分支。随后 SECURITY DEFINER 查询直接返回目标数据。

本地结果：未配对 C 调用 `get_status(A)`，获得 A 的 `lat=25.01`、`lng=121.51`、`battery=66`。无需先伪造配对。此处泄露仍受目标共享开关影响，但已经违反未配对账号隔离要求。

**修改要求**：显式处理对象为空的情况，或采用 NULL 安全的比较。将对象 ID 取到变量，明确只允许自己或有效对象。

**验收**：未配对 C 指定 A 的 ID 必须被拒；已配对 B 指定无关 D 也必须被拒；自己、正常对象、缺省读对象分别测试。

## N02 暂停仍能读取历史位置和用机

**级别：阻断。证据：本地复现。**

位置：`003-hardening.sql` 第 190 行；`001-schema.sql` 第 320–363 行。

003 删除了对象读取 `user_status` 的策略，但历史位置策略仍通过该表判断暂停：

```sql
and not exists (
  select 1 from public.user_status us
  where us.user_id = public.my_partner_id()
    and us.paused_until > now()
)
```

对象现在看不到这行，子查询返回空集，`NOT EXISTS` 反而为真。结果是修复原表读取路径时，使历史位置的暂停判断失效。

另外，`daily_usage` 和 `app_usage` 的旧策略只检查 `share_usage`，003 没有加入暂停条件。当前 Spec 已将暂停定义为三类全部停止共享，因此这些读取也违反新契约。

本地结果：A 暂停后，B 的 `get_status(A)` 返回空坐标，直接读 `user_status` 也为空；但 B 仍从 `location_points` 得到坐标，从 `daily_usage` 得到 `screen_on_ms=900000`，从 `app_usage` 得到应用明细。

**修改要求**：让所有数据入口使用可靠的共享判定，避免在调用者不可见的表上通过否定查询判断暂停。可以采用严格限定返回值和身份的权限辅助函数，或收回原始表读取权限，统一使用受控接口。

**验收**：暂停后用对象身份分别查询状态、历史位置、每日用机、应用明细，不可只验证 `get_status`。

## N03 关闭电量共享仍会泄露历史电量

**级别：高。证据：本地复现。**

位置：`001-schema.sql` 第 58–68、320–335 行；Spec 第 5 节。

`location_points` 包含 `battery` 和 `charging`。位置共享开启时，对象可以读取整行；其中的电量没有受 `share_battery` 控制。

本地结果：A 设置 `set_sharing(true,true,false)`，B 的状态接口电量为空，但历史位置仍返回 `battery=66`、`charging=true`。

**修改要求**：分别控制历史位置和历史电量的可见字段。不要把当前状态接口的遮蔽等同于所有入口都遮蔽。

**验收**：位置开启、电量关闭时，所有允许对象访问的表或接口均不能返回电量和充电状态。

## N04 成员表允许用户伪造关系

**级别：高。证据：本地复现。**

位置：`003-hardening.sql` 第 35–37、47–50 行；Spec 第 5 节权限表约第 280 行。

Spec 写成员表只能通过函数写入，但 INSERT 策略允许用户直接写自己的 `user_id`，没有检查其是否为目标关系的成员。`my_partner_id()` 又相信这条记录：只要调用者不是 `user_a`，就返回 `user_a`，没有再确认调用者等于 `user_b`。

本地结果：C 在知道 A/B 的关系 ID 后，插入 `(C, AB关系ID)` 成功，随后 `my_partner_id()` 返回 A，C 可以读取 A 的用机数据。此问题以已知有效关系 ID 为前提，UUID 不能作为授权边界。

**修改要求**：删除普通用户直接插入成员表的通道；函数查询同时验证关系成员身份。迁移回填遇到已有冲突时应报错或给出修复清单，不能用 `ON CONFLICT DO NOTHING` 掩盖不一致。

**验收**：普通用户不能自行加入任意关系；正常配对仍通过受控函数完成；两侧关系查询一致。

## N05 快照版本检查仍存在并发窗口

**级别：高。证据：静态分析，尚未多连接复现。**

位置：`003-hardening.sql` 第 411–440 行。

顺序测试确实通过：先写 10:15，再写 10:00，后者返回 -1，数据保持新版。但版本比较使用普通 SELECT，后面的 UPSERT 无条件覆盖。两个请求可同时读到 09:00，分别认为 10:00 和 10:15 都可写；若新版先提交，旧请求随后仍能覆盖。

事务保证一次调用内部原子提交，不会自动让读后写判断具备并发互斥。

**修改要求**：在 UPSERT 的冲突更新条件中原子比较版本，并根据实际是否接受决定应用列表是否替换；或先取得稳定的按用户、日期互斥锁，再比较和写入。仅对已有日报行加锁，还须处理当天第一条记录不存在的情况。

**验收**：使用两个独立连接覆盖已有日报和空日报两种并发场景；最终日汇总与应用列表均须属于最新快照。保留当前顺序乱序测试。

## N06 恢复后立即返回旧坐标

**级别：中。证据：本地复现。**

位置：`003-hardening.sql` 第 242–249、474–491 行；Spec 第 11 节约第 556 行、V8。

恢复仅清除 `paused_until`，未清除旧位置，也没有记录恢复后需要新点的状态。此时 `get_status` 立即返回暂停前的坐标。定时暂停到期也有同样情况。

本地结果：A 暂停后直接恢复，尚未上报新点，B 已取得原来的 `25.01,121.51`。这与拿到新点前只显示正在定位的契约不一致。

**修改要求**：明确服务端或客户端如何判断当前点采集于恢复之后。若要求任何调用者都读不到旧点，应在服务端执行；新打开查看端也应得到一致结果。

**验收**：分别测试手动恢复、自然到期、恢复后立即打开新查看端，以及积压旧点补传。

## N07 实时发布范围和新用户初始化未完成

**级别：中。证据：本地 SQL 复现，实时发送未测。**

位置：`003-hardening.sql` 第 175–184、489–491、518 行；`001-schema.sql` 第 147–172、386–387 行。

1. 003 只添加 `presence`，没有移除旧发布表。本地 `pg_publication_tables` 仍有 `user_status`、`location_points`、`presence` 三张表。因此只发布 presence 的声明不成立。发布表存在不等于消息必然发送，但结合 N02 的历史位置读取权限，不能认定实时泄露路径已关闭。
2. 003 只回填已有用户的 presence，没有更新注册触发器。迁移后注册的新用户没有 presence 行，`set_pause`、`set_sharing` 的 UPDATE 匹配零行，不产生刷新信号。首次位置上报才会补建；纯查看端则可能一直没有这行。

**修改要求**：把原始敏感表移出发布集合；为新用户创建 presence，或在设置函数中 UPSERT。确认只有被授权的对象能够订阅信号。

**验收**：检查发布表集合；新用户在首次定位前切换暂停或开关也能通知查看端；线上抓取消息体验证字段，而非只看客户端订阅代码。

## N08 统计验收仍需建立共同口径

**级别：中。证据：文档核对。**

位置：Spec 第 9、12、14 节，约第 423、429、572–573、628 行。

时长和排名已拆开，这是改进。但仍将系统数字健康作为唯一正确值，没有证明亮屏、应用前台和系统统计含义一致；短区间过滤、六小时截断、自身应用排除也仍然保留。第 12 节允许 60 秒内的名次互换，V6 却要求顺序完全一致。

**可直接实施的补法**：

- 算法单测使用固定事件序列，以 Spec 明确规则计算期望值。例如跨午夜连续亮屏 20 分钟，应按两侧各 10 分钟核对；同时定义半开时间区间，避免用 23:59:59.999 造成毫秒缺口。
- 对过滤短时段、超过六小时、同包多 Activity、尚未结束的区间分别给输入和期望输出。
- 排名只对同一过滤集合计算，明确相同时长的排序及第 15 名边界。
- 系统数字健康保留为真机对照项。先记录口径差异与试测偏差，再决定是否保留每日 60 秒目标。
- 将同一条排名容差同步到 V6。

本次不建议未经数据支持地换一个误差数字。

## N09 留存与冻结声明仍有事实错误

**级别：中。证据：文档核对。**

- Spec 约第 670 行和处理记录写不启用 pg_cron 时留存到 8 天。实际上没有其他清理机制时，数据不会自动过期。启用每日清理且持续成功执行，才会产生约 7 至 8 天的留存窗口；漏跑会更长。
- README 写 003 待执行，同时写规格已冻结可派单；Spec 约第 121 行又将 003 列为已经在库里运行。处理记录则要求补证据后才能冻结。应分别记录设计版本、已部署迁移、验证结果，不混为一个状态。
- Spec 页头版本仍为 1.1，变更记录和页脚已经是 1.2。
- PRD G1 仍写暂停期间用机照常，新增 G2 又写暂停覆盖三类；常去点聚类也仍在 PRD 的首版需求里。
- 查看端要求关闭共享即不上报，但 Spec 设置表仍定义开关只影响对象读取。需要独立的纯查看模式或明确采集条件，避免实施者把两个不同含义混用。

## 对修改者新增判断的核对

**修改函数返回类型需要先删除旧函数：认同当前修法。** 003 已加入对应 DROP。本地 001→002→003 执行通过；这是本地验证，不代表线上已迁移。

**`report_usage` 返回 -1：可接受，属于接口设计取舍。** 结构化返回更清楚，但现阶段不构成必须改签名的缺陷。优先修并发版本判断。

**上报中三处写入任一失败会留下部分数据：不适用于当前函数。** 当前写入在同一数据库函数调用的事务中，没有吞掉异常后继续提交的逻辑。测试在写 presence 时主动抛错，前面的新增位置点计数为 0，状态坐标也保持原值，证明整体回滚。

原子回滚不等于所有一致性问题都已消失：旧快照并发覆盖、条件更新跳过旧点、直接表写入绕开函数，都应分别检查。不能用事务原子性为这些问题背书，也不应把它们称为某条 SQL 失败后半提交。

参考：[PostgreSQL IF 语义](https://www.postgresql.org/docs/18/plpgsql-control-structures.html)、[RLS 策略执行权限](https://www.postgresql.org/docs/17/ddl-rowsecurity.html)、[事务回滚](https://www.postgresql.org/docs/18/sql-rollback.html)。
