纯查看模式的正确顺序

  1. 先 set_collect_enabled(false)，停掉未来上报。
  2. 再 set_sharing(false,false,false)，撤掉对方可见性。
  3. 两步都成功才算进入纯查看模式。第二步失败就停在「已停止采集，仍在共享」，只重试第二步。
  4. 两步都幂等，重复调用不报错。

p_apps 必填，语义是整日全量替换。传 null 会被拒绝（invalid_payload）；传 [] 表示当天没有应用数据，清空旧明细；传数组就是这一天的完整清单，先删后插。

位置点相反，是逐条追加（user_id + recorded_at 幂等），超过 50 点才拆批。两者的超限处理不要混用。

06错误形状

PostgREST 统一返回 {"code","message","details","hint"}。业务错误写在 message 里，HTTP 状态码不作业务判定依据。

message触发客户端动作
not_authenticated没有有效 JWT清 token，回登录
not_allowed读的不是自己也不是对象回落到读对象，不重试
invalid_payload必填字段缺失、类型不对、取值越界（坐标 ±90/±180、电量 0–100、时长计数为负）记日志丢弃，不重试
batch_too_large位置超 50 点拆批重发，每批 ≤50
apps_too_many应用超 20 行本地取 Top 20 后整体重发，禁止拆包
future_timestamp采集时刻超过服务端时间 +10 分钟用服务端时间校正后重发；不要循环重试同一个未来时间
invalid_code码不存在、已用、已过期提示重新输入，不清输入框
cannot_pair_self输了自己的码提示换对方的码
already_paired自己已有关系刷新进主页
partner_already_paired对方已有关系提示让对方先解绑（v0.1 用暂停兜底）
collect_disabled纯查看设备调上报停上报循环，不改共享
permission denied for table …绕过函数直写受控表（数据表、settings、presence，或改 profiles 的非授权列）不允许发生，属实现缺陷
SQLSTATE 会漏出来，别只认 business code

函数内部的业务错误统一是 P0001，message 就是上表那些词。但函数里读不到的路径仍可能抛出原生错误：类型转换失败 22P02、日期格式错 22007、非空约束 23502、整数越界 22003。客户端按 message 精确匹配 → 未命中就走「未知错误」分支，不要把 HTTP 404/400 当业务判据。

004 之后，校验类错误已经全部转成 invalid_payload；仍看到 22P02／23502 说明有字段没进校验，属于要回来补校验的缺陷，不是正常分支。

一批里有一个坏点，整批不写

report_locations 先校验全部点再插入，任何一点不合格整批拒绝，不会写一半。客户端要根据 received/inserted 判断：只有 received == 提交条数 才算成功。要定位坏点是哪一条，客户端在本地先按同样规则筛一遍再发。

07Kotlin 线格式

客户端只在网络层用这些类型。JSON 键保持 snake_case，Kotlin 属性用 camelCase 配 @SerialName。

时间不能假设 Z 后缀。请求侧我们统一发 2026-10-26T04:00:00Z；响应侧由 PostgreSQL 按会话时区序列化，实测会拿到 2026-10-26T00:00:00+00:00 甚至 +08:00。所以 DTO 里保持 String，业务层用 OffsetDateTime.parse 再转 Instant；不要用 Instant.parse（它只吃 Z），也不要用字符串比较判断时间先后。

08口径

项定死的口径
坐标全链路 GCJ-02。高德回调直接上报，不做 WGS-84 转换；显示也只按 GCJ-02 用
时区日切按 Asia/Shanghai；请求时间戳统一发 UTC 带 Z，响应可能带任意偏移，按 ISO-8601 解析
时钟容限采集时刻最多允许比服务端时间超前 10 分钟，超过报 future_timestamp；历史补传不设下限
直写边界数据库强制的只有：四张数据表、settings、presence 全禁直写，profiles 只许改两列。devices 允许本人整行直写，这是约定上的例外，不是漏洞
时长单位一律毫秒，字段名带 _ms
电量整数百分比 0–100
精度米，accuracy 越小越准；未知传 null
状态判定只用 server_now 与 paused_until 比较，不用手机时钟
无数据last_report_at is null 才是「从未上报」；坐标 null 只代表被遮蔽
幂等位置靠 user_id + recorded_at；用机靠 captured_at
成功判据位置看 received == 提交条数，不看 inserted；用机看返回值 ≥ 0，-1 是旧快照
订阅只订 presence，过滤 user_id=eq.<对象id>；收到后重新拉 get_status 与 get_usage

09客户端不能做的事

  • 不能直接 INSERT / UPDATE / DELETE 四张数据表。没有写策略，也没有表级写权限，会直接报 42501。
  • 不能直接写 settings 或 presence。改开关走 set_sharing / set_collect_enabled，刷新信号由上报与设置函数维护。
  • 不能改 profiles 里 nickname、avatar_url 以外的列，别拿邮箱或创建时间当可写字段。
  • 不能直接读对象的 user_status、location_points、daily_usage、app_usage。查出来是空集，不是报错。
  • 不能自己写 couple_members 或 couples。配对只走两个函数。
  • 不能在 report_usage 里把 p_apps 传 null 当「不动明细」，现在会被拒；要不动就别调这个函数，要替换就发完整数组。
  • 不能把超过 20 条的应用拆成几包发。应用是整日替换，后一包会覆盖前一包，最后只剩最后一包。
  • 不能把 captured_at 设成未来时间。未来快照会长期占住版本号，后续真实快照全被当成旧的丢弃；超过 10 分钟会直接被拒。
  • 不能假设时间字符串以 Z 结尾，也不要用字符串比较时间先后。
  • 不能把「恢复」当成「清空数据」。恢复只清 paused_until 并写 resumed_at，旧点还在库里，靠遮蔽不让看。
  • 不能把纯查看模式理解成「关采集就隐身」。要两步：关采集 + 关三类共享。
